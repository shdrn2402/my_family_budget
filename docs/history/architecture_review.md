# Отчет о ревизии архитектуры и базы данных

## Контекст
В ходе обсуждения архитектуры финансового бота были предложены новые концепции ведения учета:
1. Использование транзитных счетов (Transit Account) для систем типа Bit/PayBox.
2. Виртуальные кошельки наличных с механизмом "Корректировки нала" (Adjustment).
3. Система двухфазного подтверждения транзакций (Draft/Pending -> Verified).
4. Разделение наличных по конкретным пользователям в рамках семьи.

Ниже представлен анализ текущей кодовой базы на предмет совместимости с этими идеями.

---

## 1. Что уже сделано

### ✅ Не противоречит и отлично дополняет концепцию
* **Блокировка ручного ввода для карт:** В `handlers/expense.py` реализована проверка `if account_type == 'card':`, запрещающая ручной ввод для банковских карт. Исключением станут счета типа `transit` (для Bit), что сохранит для них гибкость ручного ввода.
* **Отрицательные суммы по умолчанию:** В коде суммы жестко конвертируются в минус (`-abs(amount)`). Это полностью соответствует формату банковских выписок (где расходы идут с минусом) и упрощает логику парсинга.
* **Система алиасов (Aliases):** В `database.py` и `expense.py` реализовано разрешение алиасов для счетов (`account_aliases`). Пользователи смогут писать "бит", "перевод", "нал жена", и система сама маршрутизирует это на правильные транзитные или виртуальные счета.
* **Защита от дублей по external_id:** В `save_transactions_bulk` используется `ON CONFLICT (external_id) DO NOTHING`. Это фундамент для будущего "мэтчинга" выписок и чеков, предотвращающий появление двойных расходов.

### ⚠️ Мешает или противоречит концепции
* **Таблица `accounts` слишком общая:** В базе у счетов есть `family_id`, но нет жесткой привязки к конкретному пользователю (`user_id`). Это противоречит идее раздельного учета наличных. Сейчас любой счет — это общий семейный котел.
* **Отсутствие поля `status` у транзакций:** Хендлеры делают жесткий `INSERT` прямо в БД без какого-либо понятия о том, подтверждена транзакция (Verified) или это черновик из ручного ввода (Draft/Pending). Без этого поля не реализовать двухфазное подтверждение.

## 2. Что еще надо сделать для реализации

На основе текущей кодовой базы, вот конкретный план действий (to-do список):

### Реформа структуры таблиц (Accounts & Transactions)
* В таблицу `accounts` добавить опциональное поле `owner_id BIGINT REFERENCES users(id)` (для персональных кошельков наличных).
* Добавить в ENUM поля `type` таблицы `accounts` значение `transit` (для Bit/PayBox).
* В таблицу `transactions` добавить поле `status VARCHAR(20) DEFAULT 'confirmed' CHECK (status IN ('draft', 'pending', 'confirmed', 'adjustment'))`.

### Маршрутизация переводов (Bit Flow)
* **Исходящие переводы (минус в выписке):** Создают транзакцию со счета `Card_Main` на счет `Bit_Transit` (чтобы мы могли потом "схлопнуть" её с ручным вводом "бит на пиццу 50").
* **Входящие переводы (плюс в выписке):** Добавлять в базу со статусом `Pending` и спрашивать пользователя: "Пришло 100₪ через Bit. Это кто-то вернул долг или доход?". Для возвратов использовать категорию "Кредиты и долги" (чтобы компенсировать расход "дал в долг").

### Команда "Корректировка нала"
* Создать новый хендлер (команду `/adjust <сумма>` или кнопку "Сверить наличные").
* **Логика:** Бот вычисляет баланс виртуального кошелька (Снятия из банкомата `+` минус ручной расход `-`), сравнивает с тем, что ввел пользователь, и автоматически пишет в таблицу `transactions` запись `Adjustment` в категорию "Неучтенные расходы" на дельту.

### Алгоритм "Мягкого Мэтчинга" (Сверка)
* При загрузке выписки бот должен пробегаться по транзакциям со статусом `draft` (введенным руками/чеками) за эти даты (±1 день). Если сумма сходится с погрешностью ~1% — обновлять статус ручной записи на `confirmed` и подшивать к ней банковские реквизиты, вместо создания новой строки.

## 3. Мои предложения по расширению/укреплению концепции

1. **Авто-пинг по "Транзитным" счетам (Gamification):**
   Раз мы делаем `Bit_Transit`, там будут "зависать" деньги. Бот должен раз в неделю проверять баланс транзитных счетов и присылать сообщение:
   > *"Привет! У вас на счете Bit зависло 350₪. Я вижу 2 перевода, которые вы не категоризировали. Давайте раскидаем их сейчас?"* — с инлайн-кнопками для быстрой сортировки.

2. **Идентификация авторов в общих картах:**
   Операции по общей дебетовой карте будут записываться с `user_id = NULL` (как семейный расход). А вот для индивидуальных кредиток можно использовать 4 последние цифры из выписки: создадим таблицу `card_bindings (card_suffix, user_id)`, чтобы парсер автоматически подставлял нужного инициатора.

3. **Упрощенная обработка Возвратов (Refunds):**
   Учитывая крайнюю редкость возвратов (например, отмена покупки), мы не будем усложнять систему линковкой транзакций. Входящие "плюсы" из магазинов будут просто записываться в "Доходы". Это сбалансирует общие финансы семьи без усложнения логики и базы данных.
